El schema y el código
dejan de poder contradecirse

Antes · el schema por un lado, el código por otro

parameters: { type:"object",
  properties:{ command:{type:"string"} },
  required:["command"] },
run: async (a) => execAsync(String(a.command))
// `a` es any.

Describes el mismo dato dos veces. Le cambias el nombre a uno y el otro se queda como estaba: compila, arranca, y el modelo manda un campo que tu código no lee.

Ahora · una sola

inputSchema: z.object({
  command: z.string().describe("El comando.")
})
// run recibe { command: string }, ya validado

De esa línea salen tres cosas, y ya no pueden discrepar:

  • El schema que ve el modelo
  • La validación: si manda comand, truena ahí y no tres capas abajo
  • El tipo, sin escribirlo aparte
El detalle que se pasa por alto

.describe()
es el manual
de la herramienta

El modelo no lee tu código. Lee el nombre, los campos y ese texto. Lo que no digas ahí, no lo sabe.

La mejora: al escribir run, el editor ya sabe que a.command es un string. Te autocompleta y te marca la errata.

Los tres, en el mismo bloque

Todo entra por el mismo writer

UI es la interfaz: la pantalla que ve tu usuario. Un artefacto es un dato que esa interfaz dibuja como componente —una tarjeta, una imagen, una vista previa— en vez de escupirlo como texto.

// abre el canal hacia la pantalla. `writer` es quien escribe en él
const stream = createUIMessageStream({
  execute: async ({ writer }) => {

    // write = mando un dato mío. El `type` le dice a React qué pintar
    writer.write({ type: "data-uso",     data: estado.uso });  // 2
    writer.write({ type: "data-captura", data: { url } });     // 3

    // merge = vuelco TODO lo que va diciendo el modelo en ese mismo
    // canal, mientras lo dice. Antes esto era mi protocolo a mano.
    const resultado = correrTurno({ mensajes, writer, estado });  // 1
    writer.merge(resultado.toUIMessageStream({ sendReasoning: true }));
  },                                          // ↑ que su razonamiento también viaje
});
La decisión que sí conservamos

Las herramientas
las corremos nosotros

Cuando el modelo pide usar una herramienta —leer un archivo, correr un comando— alguien tiene que ejecutarla de verdad.

Podríamos dejárselo al SDK

Le entregas la función y él la llama. Menos código todavía.

Pero entonces nadie mide

No sabrías cuánto tardó ni si falló. El modelo no reporta nada de eso.

Así que la corremos nosotros, le tomamos el tiempo, y ese dato sale a la pantalla por la misma conexión.

El problema real

DeepSeek no ve

Y este agente construye interfaces: sin ojos escribe el código pero no comprueba el resultado, que era lo que lo hacía útil.

La solución

Otro modelo mira por él. Para el agente sigue siendo una sola herramienta: pide una captura y recibe una descripción, sin enterarse de que hubo dos modelos.

El caché
30×

más barato que entrada fresca.

Y no se pide

Es automático, por prefijo, y vive en disco: por eso dura de horas a días, no de minutos. Sin prompt_cache_key, sin previous_response_id.

Lo que pone el SDK

El caché es de DeepSeek. Lo que da el SDK es verlo: cada paso te entrega los contadores del proveedor en el mismo lugar, y de ahí salen los números de abajo.

onStepFinish({ providerMetadata }) {

}

La letra chica del 30×

El caché solo sirve si
el principio no cambia

El descuento de hace un momento no es gratis: llega solo si tu petición empieza igual que la anterior. El proveedor las compara desde la primera palabra, reusa todo lo que venga igual al inicio, y en cuanto encuentra una diferencia deja de reusar de ahí hasta el final.

const SYSTEM = `Eres un agente.
Hoy es ${new Date().toISOString()}.   ← cambia cada vez
...`

La diferencia está en la segunda línea, así que de ahí en adelante no se reusa nada. Nunca.

Funciona igual, solo cuesta diez veces más, y nada te avisa.

El execute · el dialecto de la API

Si sale la pregunta: este código NO usa la Responses API. @ai-sdk/deepseek llama a /chat/completions — verificado en el paquete. DeepSeek V4-Pro sí soporta Responses de forma nativa, pero el provider del SDK no pasa por ahí.

Y eso no le quita nada al caché: el caché de DeepSeek es automático por prefijo y no depende de Responses. La prueba son los 256 tokens de la slide siguiente, medidos sobre chat/completions. Responses sirve para otra cosa — que el servidor guarde el hilo con previous_response_id.

Lo interesante es el meta-punto: el SDK te deja no tener esta conversación. Cambias el provider y el dialecto es su problema.

El caché

No des precios por millón de tokens en cámara: cambian y el video vive meses. El «30×» y los 256 tokens medidos aguantan mejor el paso del tiempo.

La trampa del prefijo

Este es el consejo que la gente va a usar el mismo día. Dilo despacio: la petición funciona igual, solo que cuesta diez veces más, y nada te avisa. No hay error, no hay warning, no hay log.
